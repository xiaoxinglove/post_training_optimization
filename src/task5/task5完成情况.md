##### **4.1 最小打卡(对应Part 02 · PT-ROLLOUT-LIFECYCLE 轨迹与策略新鲜度,Part 02 · PT-RL-SYSTEM 采样、训练与奖励系统,08 轨迹生命周期与环境交互）**

（1）一条轨迹需要同时记录哪五类信息？正常生命周期如何迁移，更新中止时应回到哪个状态？为什么“检查可用与写入预留”必须构成一次不可分割的状态迁移？

1. 一条轨迹需要同时记录五类信息，保证训练数据可追溯、可计算、可恢复。

   ①轨迹身份与任务来源：轨迹 ID、任务 ID、数据及环境版本，用于去重和固定比较起点；

   ②行为策略身份：生成轨迹的策略版本与产物哈希，用于确认来源和检查策略滞后；

   ③生成条件：分词器、采样参数、随机种子等，用于明确生成约定；

   ④动作证据：模型动作、动作掩码及行为策略对数概率，用于确定有效训练位置和计算概率比率；

   ⑤奖励与生命周期状态：奖励分量、验证器版本、终止原因、预留者和消费批次等，用于判断反馈有效性及消费情况。环境观察也应保存为上下文，但不能当作模型动作计入策略损失。

2. 正常生命周期为 `generated → rewarded → reserved → consumed`，更新确认中止且未提交时，应从 `reserved` 回到 `rewarded`。 四个状态分别表示已生成、奖励就绪、已被某次更新独占预留、更新已成功提交。中止只取消本次预留，并不使已有奖励失效，因此应释放预留、保留奖励，而非退回 `generated`。只有更新成功提交后才能登记为 `consumed`；若提交结果不明，应先隔离核对，避免错误释放导致重复消费。

3. “检查可用与写入预留”必须原子完成，以保证同一轨迹不会被两个更新同时领取。若先检查、后写入，学习器 A、B 可能同时读到 `rewarded`，随后各自将轨迹加入更新批次，造成重复消费。正确机制是：仅当状态仍为 `rewarded` 且修订号与读取时一致，才一次性写入 `reserved`、预留者及递增后的修订号；条件不满足则返回冲突，不修改记录。该操作须由事务、锁或原子比较交换保证，不能仅依赖普通代码中的“先判断、再赋值”。

   
   （2）为什么不同阶段的原始处理率不能直接比较？如何用阶段倍率把原始处理率换算为等价处理率？流水线容量、队列余量分别如何定义，队列余量为负说明什么？

1. 原始处理率不能直接比较，因为各阶段的计量对象不同。生成阶段可能统计“轨迹/秒”，奖励阶段统计“评分/秒”，学习阶段统计“更新/秒”，一次更新又可能消耗多条轨迹。因此，原始数值大小不能直接代表处理能力强弱，必须先统一工作单位和工作量口径。

2. 等价处理率等于原始处理率除以阶段倍率，即 \(c_j=q_j/m_j\)。其中，\(m_j\) 表示每个统一工作单位需要阶段 \(j\) 处理的对象数。相除可以消去本阶段对象的单位，得到统一的“工作单位/秒”。例如，每个提示组包含4条轨迹，奖励阶段处理80条轨迹/秒，则等价处理率为 \(80/4=20\)组/秒；若学习器每8组更新一次，则倍率为 \(1/8\)，仍按相除换算。

3. 流水线容量是各阶段等价处理能力的最小值，即 \(C_{\mathrm{pipe}}=\min_j c_j\)。因为每份工作都必须经过所有阶段，最慢阶段限制最终输出速度。例如三个阶段分别能处理30、20、24组/秒，则容量为20组/秒，第二阶段是瓶颈。该公式适用于各阶段能够并发、资源相对独立的流水线；共享资源、通信和同步开销可能进一步降低实际容量。

4. 队列余量是服务能力与到达率之差，表示处理能力还剩多少。若各阶段都按外部需求率 \(\lambda\) 评估，则阶段余量为 \(s_j=c_j-\lambda\)，整体余量为 \(s_{\mathrm{pipe}}=C_{\mathrm{pipe}}-\lambda\)，单位均为“工作单位/秒”，不是缓冲区剩余空间。正值表示有处理余量，零表示处于临界状态；常见随机排队模型通常要求严格正余量才能稳定，不能认为“余量非负就一定稳定”。

5. 余量为负说明处理能力不足；若实际到达持续超过服务能力，队列就会不断积压。例如实际到达24组/秒、只能处理20组/秒，则平均每秒积压4组。严格地说，积压增长率应按该队列的实际到达率 \(a_j\) 计算，即 \(a_j-c_j\)，不能一律使用外部输入率，因为上游瓶颈或反压可能已经限制流入。负余量也不代表该阶段一定是全局瓶颈；增大缓冲区只能推迟满载，根本措施是提高处理能力或降低输入负载。



**4.2 学有余力增项1（对应Part 02 · 51 在线 DPO，09 在线训练交付与执行系统）**  
（1）为什么在线 DPO 不能只看 “反馈有没有进来”，还必须跟踪 policy freshness？policy freshness 应该在哪一个环节被记录或检查？请结合闭环步骤说明。 

1. **“反馈有没有进来”衡量反馈通路是否畅通，policy freshness 衡量这些反馈是否跟得上策略的更新。**

   在线 DPO 的目的是让模型持续从自身当前的行为中获得偏好信号。但生成、标注和训练之间存在延迟：刚收到的反馈，可能评价的是多轮更新之前的模型。因此，反馈的到达时间新，不代表生成它的策略新。如果不跟踪生成策略与当前训练策略的差距，就可能把“旧策略的反馈持续流入”误判为“当前策略正在得到有效纠正”，使训练长期围绕旧问题展开，遗漏当前模型的新错误。旧反馈仍可能有用，但仅凭“收到反馈”无法判断在线闭环是否有效。

2.  应当做到生成时记录、训练前检查、更新后验证回流。沿“生成候选 → 收集反馈 → 构造偏好对 → DPO 更新 → 评估发布 → 再次生成”的闭环：生成时记录实际使用的策略版本和生成时间；收集反馈、构造偏好对时保留这些信息，不能用反馈到达时间重置样本年龄；每次取出训练批次时，检查生成策略与当前策略的版本或更新步数差，必要时评估分布差异，并决定继续使用、降权或重新采样；评估发布后，确认采样服务实际加载了新权重，使下一轮反馈确实评价更新后的行为。


（2）为什么在线 DPO 中 “参考模型永远冻结” 可能成为一个问题？如果选择更新参考模型， stability boundary（稳定性边界） 意味着在更新 ref 时必须同时控制什么？

1. 固定参考模型可能逐渐成为陈旧的优化基线。参考模型的目的是约束策略偏移、保持训练稳定；但在线 DPO 的策略和采样分布不断变化，始终围绕初始模型施加约束，可能限制进一步改善。同时，DPO 衡量的是相对参考模型的偏好改善，部分样本即使尚未被正确排序，也可能因相对旧参考模型已改善很多而出现梯度衰减。因此，单轮优化期间冻结有助于稳定，跨所有轮次永久冻结则可能造成学习瓶颈。

2. 必须联合控制参考模型的漂移、策略的更新强度，以及二者形成的有效约束。具体包括 ref 更新的频率与混合比例，以及策略学习率、每轮更新步数和 DPO 的 \(\beta\)：更新 ref 会重置相对偏好基线，进而改变梯度，不能孤立调整。还须同时监测策略相对当前 ref 的局部偏移，以及相对初始模型的累计偏移；否则，即使策略始终贴近当前 ref，二者仍可能共同漂移，逐步放大偏好噪声、损害原有能力。
