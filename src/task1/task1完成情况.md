## 4.1 最小打卡(对应Part 02 · 32 SFT 数据准入与长度审计,Part 02 · 13 SFT 训练循环）

1.为什么在检查训练—评测泄漏（Split Leakage）时，只比较“任务输入指纹”而不把目标回答（response）纳入比较范围？如果把回答也包含进去，会产生什么漏洞？  

检查训练—评测泄漏的目的是维护评测数据相对于训练数据的独立性，使评测结果真实反映模型对未见样本的泛化能力。

任务输入包含指令、具体输入及必要上下文，决定了题目的身份；目标回答则是该题的一种标注，可能存在不同措辞、推理过程或多个合理版本。因此，应根据规范化后的任务输入生成指纹，检查训练集与评测集是否存在重叠。同一输入即使对应不同回答，也不能视为相互独立的新任务。

会产生“改写回答即可绕过泄漏检查”的假阴性漏洞，使评测混入对已见任务的记忆，可能高估模型的泛化能力。



2.为什么数据审计要求“汇总独立拒绝原因”而不是“发现第一项风险就立即停止”？多重风险同时存在时，对后续的模板、标签及序列拼接处理有什么影响？  

因为数据审计既要判断样本能否使用，也要完整记录问题，为风险统计、来源定位和修复复查提供依据。同一样本可能同时违反多个可独立成立的准入条件；发现第一项就停止，会使其他风险被检查顺序掩盖，导致风险分布统计失真，修复时也容易遗漏问题。

模板层面，角色错位、特殊标记缺失或重复会破坏对话边界；标签层面，必须依据最终模板化、分词后的序列构造训练标签与损失掩码，否则可能把用户内容误作回答监督，或漏掉应监督的回答。序列拼接层面，必须同步维护 token、标签和样本边界；若要求样本之间相互独立，还须采用相应的注意力隔离机制，单独添加 EOS 并不能自动阻止跨样本注意力。



3.语言模型预训练（Pre-training）与监督微调（SFT）都使用 Next-Token Prediction 和交叉熵损失，但两者的监督范围和优化侧重点有着本质不同。说明为什么在 SFT 中不能让模型对整个序列（包括 prompt）都计算损失？如果不加限制会带来什么隐患？  

prompt 仍作为上下文参与注意力计算，屏蔽其损失不等于让模型忽略输入。

主要风险是监督权重失衡和优化目标偏移。当逐 token 等权计算损失时，长 prompt、短回答会让输入预测占据绝大多数监督项。



4.在计算一个 Batch 的 SFT 损失时，为什么正确的做法是“先累加全部有效监督位置的损失，再除以整个 Batch 的有效监督 Token 总数”？如果直接对 Batch 内各个样本的平均损失求均值（即“按样本数等权平均”），会带来什么问题？

因为在每个有效监督 Token 等权的目标下，Batch 损失应表示所有有效预测位置的平均交叉熵。

这会引入与有效监督长度成反比的 Token 权重：若 Batch 有 \(B\) 个样本，第 \(i\) 个样本中每个有效 Token 的权重就变为 \(1/(Bn_i)\)。例如，两条回答分别有 10 和 100 个有效 Token，按样本等权平均后，短回答中每个 Token 的权重是长回答的 10 倍。
